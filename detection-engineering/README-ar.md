# هندسة الكشف

> **الحالة:** أساس مسودة — لا يُعد أي كشف تشغيلياً أو متحققاً منه لمجرد وجود مواصفته أو SPL.

## الغرض

توفير منهج متسق قائم على الأدلة لتصميم الكشوف وتوثيقها واختبارها وضبطها وصيانتها وإيقافها عبر وحدات SOC-LAB. يراعي الإطار SIEM ويركز على السلوك القابل للملاحظة والقيمة التحقيقية.

## حدود المنصة الحالية

يستخدم خط أساس المختبر الحالي **Splunk Enterprise فقط**. وقد تستخدم أمثلة الكشوف وعمليات البحث SPL. ولا يعتمد المشروع على Splunk Enterprise Security. لا تفترض توفر البحث الترابطي المميز أو التنبيه القائم على المخاطر أو محتوى خاص بـ ES.

## الملكية والمواضع

- توضع الكشوف القابلة لإعادة الاستخدام وعمليات البحث المشتركة هنا.
- يوضع منطق الكشف الخاص بالتمرين وأدلة السيناريو ومهام المتعلمين في وحدة `lectures/*/` المناسبة.
- يوضع إعداد الجمع الخاص بالمصدر في `lab-environment/`.
- لا تكرر القوالب المعتمدة داخل الوحدات.
- يصوغ مهندس المحتوى؛ ويراجع مراجع الجودة باستقلال؛ ويعتمد مالك المشروع.

## حالات الكشف

استخدم حالة واحدة لكل كشف: `planned` أو `draft` أو `in-review` أو `approved` أو `implemented` أو `validated` أو `tuning` أو `deprecated`.

الاعتماد والتنفيذ والتحقق حالات منفصلة. فقد يكون الكشف معتمداً دون تنفيذ، أو منفذاً دون تحقق، أو متحققاً منه لنطاق اختبار محدد فقط.

## الحد الأدنى للجودة

يجب أن يحدد كل كشف سلوكه القابل للملاحظة وتبعيات البيانات وSPL والمخرج المتوقع واعتبارات الإيجابيات الكاذبة وإرشادات فرز المحلل ومواءمة ATT&CK (عند وجود ما يدعمها) وحالات الاختبار والقيود والمالك وأدلة التحقق. نقص البيانات مانع، وليس مبرراً لاختلاق أسماء حقول أو نتائج.
