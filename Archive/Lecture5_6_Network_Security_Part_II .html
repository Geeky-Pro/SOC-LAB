◆ TCPDUMP

Saving a Capture File

Watching packets scroll by is fine for a quick check, but real analysis needs a saved file you can revisit, share, or load into Wireshark. The -w flag writes raw packets to disk instead of printing them.

saving a capture
$ sudo tcpdump -i eth0 -w capture.pcap # -w capture.pcap → write raw packets to capture.pcap # console stays quiet — packets are being written, not printed $ sudo tcpdump -i eth0 -c 500 -w capture.pcap # stop automatically after 500 packets
-w <file>Write captured packets in raw (binary) form to a file.
.pcapStandard capture file extension — readable by tcpdump, Wireshark, and most analysis tools.
-c <n>Stop the capture automatically after n packets — useful for bounded, repeatable saves.
Ctrl+CStops an open-ended capture manually and finalizes the file.

Why this matters: a saved capture is evidence — the same file can be reopened days later, handed to another analyst, or dropped straight into Wireshark for a visual look.

◆ TCPDUMP

Reading a Saved Capture

Once traffic is saved, -r reads it back — printing packets exactly as if they were captured live. Every filter and flag we already know still works.

reading a capture
$ tcpdump -r capture.pcap # replays every packet stored in capture.pcap $ tcpdump -r capture.pcap port 443 # still works with capture filters — only show port 443 traffic
-r <file>Read and print packets from a saved capture file instead of a live interface.
Filters still applyCapture filters (host, port, protocol) narrow down what's read, not just what's captured.
◆ TCPDUMP

Timestamp Flags

Timestamps matter a lot in an investigation — timing tells you what happened first, how fast something moved, and helps you correlate with logs elsewhere. tcpdump's -t family of flags controls how timestamps print.

same packet, different -t levels
# default (wall-clock time, no flag) 14:22:05.123456 IP 10.0.0.5.51422 > 93.184.216.34.443: Flags [S] # -t → no timestamp at all IP 10.0.0.5.51422 > 93.184.216.34.443: Flags [S] # -tt → raw Unix epoch seconds 1721394125.123456 IP 10.0.0.5.51422 > 93.184.216.34.443: Flags [S] # -ttt → delta (ms) since the previous printed packet 000000.045213 IP 10.0.0.5.51422 > 93.184.216.34.443: Flags [S] # -tttt → full date + wall-clock time 2026-07-19 14:22:05.123456 IP 10.0.0.5.51422 > 93.184.216.34.443: Flags [S]
-tSuppresses the timestamp entirely — cleanest output when timing doesn't matter.
(default)Prints wall-clock time in HH:MM:SS.ffffff format.
-ttPrints raw Unix epoch time — easy to sort and script against.
-tttPrints the time delta since the previous packet — great for spotting bursts or gaps.
-ttttPrints full date and wall-clock time — best for correlating with other logs.
◆ TCPDUMP

Useful Display Flags

Beyond timestamps, a handful of flags control exactly how much of each packet gets printed — from just the header down to the raw payload bytes.

-A ascii output
$ tcpdump -r capture.pcap -A port 80 # prints payload as ASCII — readable HTTP requests, cookies, etc. GET /login.php HTTP/1.1 Host: example.com Cookie: session=abc123...
-c <n>Stop after printing/capturing n packets.
-APrint packet payload as ASCII text — ideal for spotting plaintext HTTP, credentials, or commands.
-xPrint packet payload as hexadecimal.
-XPrint payload as hex and ASCII side by side — the most complete view of raw bytes.
-nDon't resolve IP addresses to hostnames.
-nnDon't resolve hostnames or port numbers to service names — shows raw port numbers too.
--countPrints only the total number of matching packets instead of printing each one — a fast way to check volume before diving into full output.

Watch for: -A only shows readable text — encrypted traffic (TLS/HTTPS) will just look like noise. It works best on unencrypted protocols like HTTP, FTP, or Telnet.

◆ ANALYZING PCAP OUTPUT

Filtering Output with grep

tcpdump's printed output is just plain text — which means every classic Linux text tool works on it. grep searches for a pattern across thousands of lines instantly.

searching capture output
$ tcpdump -r capture.pcap -n | grep "192.168.1.50" # only lines mentioning this specific IP address $ tcpdump -r capture.pcap -n | grep -c "Flags \[S\]" # -c here counts matching lines → how many SYN packets total $ tcpdump -r capture.pcap -A | grep -i "password" # -i → case-insensitive search inside ASCII payloads
grep "pattern"Prints only the lines that contain the given pattern.
-iCase-insensitive matching.
-cCounts matching lines instead of printing them (grep's own -c, not tcpdump's).
-vInverts the match — shows lines that do not contain the pattern.
-EEnables extended regex — lets you use | (or), +, ?, and {} without backslash-escaping them.

The pipe (|): the pipe symbol sends tcpdump's output directly into grep as input — this is the pattern behind everything on the next slide too.

◆ ANALYZING PCAP OUTPUT

cut, sort & uniq

Chaining a few more tools together turns raw output into a real answer — like "who is talking the most on this network?" This exact pattern shows up constantly in log analysis.

"top talkers" one-liner
$ tcpdump -r capture.pcap -n | cut -d' ' -f3 | cut -d'.' -f1-4 | sort | uniq -c | sort -nr | head # cut -d' ' -f3 → pull out the 3rd space-separated field (source IP.port) # cut -d'.' -f1-4 → trim off the trailing .port, keep just the IP # sort → group identical IPs together (required before uniq) # uniq -c → collapse duplicates into "count value" # sort -nr → rank counts from highest to lowest # head → show just the top results
cut -d -f-d sets the delimiter, -f picks which field(s) to keep.
sortSorts lines alphabetically/numerically — groups duplicates next to each other.
sort -n / -nrSorts numerically; -r reverses it to descending order.
uniqRemoves adjacent duplicate lines — must be pre-sorted to work correctly.
uniq -cPrefixes each unique line with how many times it occurred.
head / tailShows just the first / last few lines of the result.

Why this matters: the same grep | cut | sort | uniq -c | sort -nr chain works on almost any text-based log — firewall logs, auth logs, web server logs — not just pcaps.

◆ WIRESHARK

What Is Wireshark?

Wireshark is a graphical network protocol analyzer — it captures and displays packets the same way tcpdump does, but with a full interface for browsing, filtering, and drilling into individual packets visually.

tcpdump

Command-line, text output, fast and scriptable — best for servers, remote sessions, and automation.

Wireshark

Graphical, interactive, deeply detailed — best for close inspection, teaching, and visual pattern-spotting.

They work together: a .pcap file saved by tcpdump's -w flag opens directly in Wireshark — capture on a headless server, analyze visually on your laptop.

◆ WIRESHARK

Capture Filters

Good news — Wireshark's capture filters use the exact same BPF syntax as tcpdump. If you know host, port, and and/or/not from Lab 4, you already know these.

capture filter field
# typed into: Capture > Options > Capture Filter (before starting) host 192.168.1.10 and port 443 tcp and not port 22
Applied before captureCapture filters decide what gets recorded in the first place — dropped packets are gone for good.
Same BPF syntaxhost, src, dst, port, net, tcp/udp/icmp/arp, and/or/not all work identically to tcpdump.
Where to set itCapture > Options, or typed directly into the filter box on the initial capture screen.

Don't confuse the two: capture filters (BPF syntax) and display filters (next slide, different syntax) look similar but aren't interchangeable — typing a display filter into the capture filter box will error out.

◆ WIRESHARK

Display Filters

Display filters use Wireshark's own field-based syntax — they only hide or show packets already captured; nothing is discarded, so you can always loosen the filter later.

display filter bar
ip.addr == 192.168.1.10 # any packet where this IP is source OR destination tcp.port == 443 # TCP traffic on port 443, either direction http # show only HTTP packets ip.addr == 192.168.1.10 && tcp.port == 443 # combine conditions with && (and) / || (or)
protocol.fieldGeneral pattern — ip.addr, tcp.port, http.request, dns.qry.name, etc.
== / !=Equals / not-equals comparison.
&& / ||Combine filters — both must match / either may match.
!Negation — e.g. !arp hides ARP traffic.
Green / red barWireshark's filter bar turns green for valid syntax, red (or pink) for invalid.

Handy shortcut: right-click any field in the packet detail pane and choose "Apply as Filter" — Wireshark writes the correct display filter syntax for you automatically.

◆ WIRESHARK

Statistics Menu

The Statistics menu gives a bird's-eye view of an entire capture in seconds — no manual scrolling required.

Protocol Hierarchy

Breaks down the whole capture by protocol layer, showing percentage and packet count for each — a quick "what kind of traffic is this?" view.

Conversations

Lists every pair of endpoints that exchanged traffic, with byte and packet counts each way — the "who talked to whom" view.

Endpoints

Per-host totals — every IP that appears, and how much traffic it sent or received overall.

File Statistics

Breaks down the capture file itself — size, duration, average packet rate, and average bytes/sec — a quick health check on the capture before diving into the traffic.

◆ WIRESHARK

Follow Stream & Export Objects

Two features turn packet-level noise into something directly readable or usable.

Follow TCP Stream

  • Right-click a packet → Follow → TCP Stream
  • Reassembles the entire conversation, both directions, in order
  • Turns dozens of packets into one readable request/response view
  • Perfect for reading a full HTTP exchange or plaintext login attempt

Export Objects

  • File → Export Objects → protocol (HTTP, SMB, etc.)
  • Pulls actual transferred files — images, documents, executables — straight out of the capture
  • Only works on unencrypted protocols, since content must be visible
  • Useful for recovering malware samples or exfiltrated files during an investigation

Wrapping up tcpdump & Wireshark: we've now covered capturing, saving, reading, filtering, and analyzing traffic two different ways. Next, we shift from analyzing traffic after the fact to detecting threats in it as they happen — with Snort.

◆ SNORT

What Is Snort?

Snort is an open-source, rule-based network intrusion detection and prevention system (IDS/IPS). Instead of us reading packets manually, Snort inspects traffic against a set of rules and alerts — or blocks — automatically.

IDS — Intrusion Detection

Watches a copy of traffic (passive) and alerts when something matches a rule. Doesn't sit in the traffic path, so it can never block anything itself.

IPS — Intrusion Prevention

Sits inline, directly in the traffic path, so it can actively drop or block traffic that matches a rule — not just alert on it.

Snort can be either: the same engine runs as a passive IDS or an inline IPS depending on how it's deployed and configured — the detection logic (the rules) stays the same either way.

◆ SNORT

How Snort Works

Every packet that reaches Snort moves through the same four-stage pipeline before a decision gets made:

1Packet Decoder
→
2Preprocessors
→
3Detection Engine
→
4Output / Logging
Packet DecoderCaptures raw packets off the wire and breaks them into their protocol layers (Ethernet, IP, TCP/UDP, etc.).
PreprocessorsNormalize and prepare traffic — reassembling fragments, handling protocol anomalies — before rules are checked.
Detection EngineCompares the processed packet against every loaded rule, looking for a match on the rule's conditions.
Output / LoggingOn a match, Snort executes the rule's action — alert, log, or (in IPS mode) drop the packet.

Rules are everything: without a loaded ruleset, the detection engine has nothing to compare traffic against — Snort is only as good as the rules it's running.

◆ SNORT

Snort's Three Modes

Snort can run at three increasing levels of capability, chosen with different command-line flags:

1
Sniffer Mode
Reads packets off the wire and prints them to the console — same idea as tcpdump, no rules involved.
2
Packet Logger Mode
Saves captured packets to disk for later review — analysis happens afterward, not in real time.
3
Network IDS Mode
Loads a ruleset and runs the full detection engine — traffic is actively compared against rules and alerts fire in real time.

NIDS mode is what we care about most: it's the mode that actually uses the rules we're about to write — sniffer and logger modes are useful for testing, but detection only happens in NIDS mode.

◆ SNORT

Snort's Files & Directories

Before running Snort, it helps to know where everything actually lives on disk — this is what the -c and -l flags point to:

default snort layout
/etc/snort/ ├── snort.conf # main config file — loaded with -c └── rules/ ├── local.rules # your own custom rules └── community.rules # official / downloaded rulesets /var/log/snort/ # alerts & packet logs — written to with -l ├── alert # alert messages (fast/full format) └── snort.log.* # raw logged packets, if logging packets too
/etc/snort/snort.confThe main config file — sets variables like HOME_NET, and includes the rule files. Loaded with -c.
/etc/snort/rules/Where rule files live. local.rules is where custom rules go; other files hold the official/downloaded ruleset.
/var/log/snort/Default log directory — where alerts and (optionally) raw packet logs are written. Set with -l.
alertInside the log directory: the plain-text file where triggered alerts are recorded, one per match.

These paths can be custom: the layout above is the common default on most Linux distros, but any config, rules, or log path can be pointed elsewhere with -c and -l.

◆ SNORT

Running Snort's Modes

Each mode from the last slide maps to a specific combination of command-line flags:

snort — three modes
# 1. Sniffer Mode — just print packets, no rules $ sudo snort -i eth0 # -i sets the interface to listen on — packets print straight to console # 2. Packet Logger Mode — save packets to disk $ sudo snort -i eth0 -l /var/log/snort # -l sets the log path — switches Snort from printing to saving # 3. Network IDS/IPS Mode — load rules, alert in real time $ sudo snort -A console -l /var/log/snort -c /etc/snort/snort.conf -q # -c loads the config + ruleset, -A sets alert style, -q runs quietly
-i <iface>Network interface to listen on, e.g. eth0 — required in every mode for live capture.
-l <path>Where to write logs (Packet Logger mode) or alerts (NIDS mode) instead of just printing to console.
-c <file>Loads a config file (with rules included) — this is what turns on the detection engine.
-A <style>Alert output style, e.g. console — controls how matches are reported.
-qQuiet mode — suppresses the startup banner and init messages, so only alerts show.
◆ SNORT

Running Snort in IPS Mode

NIDS mode only watches traffic — it can alert, but the packet still reaches its destination. To actually block traffic, Snort has to run inline, as an IPS. Three things change together:

-QSwitches Snort from passive to inline mode — traffic is intercepted before it reaches its destination, not just copied and observed.
--daqSelects the inline acquisition module that actually routes packets through Snort — afpacket bridges two NICs so traffic passes through Snort on its way between them.
drop (in rules)Rules must use the drop action instead of alert — alert still only logs a match, it never blocks the packet.
snort — inline (IPS) mode
# AFPACKET inline mode — bridges two interfaces so traffic flows through Snort $ sudo snort -q -A console -i enp0s3:enp0s8 -c /etc/snort/snort.conf --daq afpacket -Q # enp0s3:enp0s8 pairs the NICs — packets in on one side are inspected, then forwarded (or dropped)

All three pieces are required: -Q without a drop rule still only alerts; a drop rule without -Q and an inline DAQ has no traffic path to actually block.

◆ SNORT RULES

Anatomy of a Rule

Every Snort rule has two parts: a header (what traffic to look at) and a set of options in parentheses (what to check for, and what to call it).

HEADER
alert tcp any any -> 192.168.1.0/24 80
OPTIONS
( msg:"Possible web probe"; content:"/admin"; sid:1000001; rev:1; )

Header Fields

actionalert, log, pass, or (in IPS mode) drop — what to do on a match.
protocoltcp, udp, icmp, or ip.
src / dst IPSource and destination address or network — any matches everything.
src / dst portSource and destination port — any matches every port.
->Direction operator — traffic must flow from the left side to the right side to match.

Common Options

msgHuman-readable description shown in the alert.
contentA specific string or byte pattern to search for in the packet payload.
sidUnique rule ID number — required, and must not collide with other rules.
revRevision number of the rule — increments each time the rule is updated.
◆ SNORT RULES

Writing a Rule

Let's put the syntax to work with two small, realistic rules.

EXAMPLE 1 — DETECT PING SWEEPS
alert icmp any any -> 192.168.1.0/24 any (msg:"ICMP ping detected"; sid:1000010; rev:1;)

alert on any ICMP packet from anywhere, headed to our 192.168.1.0/24 network, on any port — label it "ICMP ping detected" and give it a unique ID.

EXAMPLE 2 — DETECT A SUSPICIOUS HTTP REQUEST
alert tcp any any -> 192.168.1.0/24 80 (msg:"Possible directory traversal attempt"; content:"../../"; sid:1000011; rev:1;)

alert on any TCP traffic headed to port 80 on our network, where the payload contains the string "../../" — a classic sign of a directory-traversal attempt.

Always pick a unique sid: custom rules should use sid numbers starting at 1,000,000 — lower numbers are reserved for the official Snort ruleset, and reusing one will cause conflicts.

◆ SNORT RULES

Applying a Custom Rule & Alert Mode

A rule only matters once it's loaded and Snort is actually watching traffic with it:

applying a custom rule
# 1. Add the rule to a local rules file $ echo 'alert icmp any any -> 192.168.1.0/24 any (msg:"ICMP ping detected"; sid:1000010; rev:1;)' >> /etc/snort/rules/local.rules # 2. Make sure snort.conf includes it include $RULE_PATH/local.rules # 3. Run in NIDS mode with alerts printed to console $ sudo snort -A console -l /var/log/snort -c /etc/snort/snort.conf -q
SAMPLE ALERT OUTPUT
[**] [1:1000010:1] ICMP ping detected [**]
07/27-14:22:05.123456 10.0.0.5 -> 192.168.1.10
ICMP TTL:64 ID:1 IpLen:20 DgmLen:84

Alert Output Formats (-A)

-A consolePrints full alerts directly to the terminal in real time — best for live demos and testing.
-A fastCompact, one-line-per-alert format — timestamp, message, and addresses only.
-A fullVerbose, detailed alert written to the log file — the default when logging to disk.
-A noneDisables alerting entirely — useful when only packet logging is needed.
◆ REPORTING

Writing the Analysis Report

Analysis isn't finished when the capture is understood — it's finished when it's written up. After analyzing a pcap file, the analyst documents the findings in a structured report:

1. Executive SummaryA short, non-technical overview of what happened, its impact, and severity — written for managers, not analysts.
2. Scope & ObjectivesWhat was analyzed (which capture, timeframe, hosts) and the question the investigation was trying to answer.
3. Methodology & ToolsThe tools and techniques used — e.g. tcpdump for capture, Wireshark for inspection, Snort for rule-based detection.
4. Findings & AnalysisThe technical detail: what the traffic showed, suspicious patterns, and how conclusions were reached.
5. Indicators of CompromiseConcrete artifacts — IPs, domains, ports, payloads, or rule matches — that others can use to detect the same activity.
6. Recommendations & ConclusionActionable next steps (block, patch, monitor, write a new rule) and a brief summary tying the findings together.

Order matters: start non-technical (executive summary) and get progressively more technical — readers should be able to stop after section 1 and still understand what happened.
